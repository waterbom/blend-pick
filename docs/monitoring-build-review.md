# 방문·트래픽·자동 점검 빌드 검토본

## 상태

- 운영 배포/main push/수집 활성화/운영 DB 변경 없음.
- 관리자 `/admin/monitoring` 및 사이드바 메뉴 추가. 기존 '오늘 처리할 일' 유지.
- 방문 통계만 관리자에 직접 조회 연결. 자동 점검·서버 트래픽은 기존 독립 보고서 유지, 관리자 결과 자동 전달은 미연결로 표시.
- `ANALYTICS_ENABLED=false`가 기본값. 페이지 수집 컴포넌트는 이 값이 true일 때만 렌더되고 API도 같은 플래그로 중단된다.

## 한 번에 검증

```bash
npm ci
npm run check:monitoring
```

이 명령은 공개 점검 격리 테스트 → 방문 수집/격리 PostgreSQL 테스트 → Next.js 프로덕션 빌드 순서다. 테스트는 운영 서버·결제·문자를 호출하지 않는다. 방문 DB 검증은 개발 의존성 PGlite를 사용한다. 빌드할 때 운영 데이터 연결 없이 검증하려면:

```bash
DATABASE_URL=postgresql://build:build@127.0.0.1:9/build SHOP_DATABASE_URL=postgresql://build:build@127.0.0.1:9/build ANALYTICS_ENABLED=false ANALYTICS_DATABASE_URL= ANALYTICS_HASH_SECRET= npm run check:monitoring
```

기존 메인/사이트맵 코드의 상품 조회 경고가 나올 수 있다. 이 모드는 컴파일·타입·라우트 생성 검증이며 운영 데이터가 포함된 화면 검증은 아니다. 이 빌드 결과물을 그대로 운영에 복사하지 말고 운영 환경에서 다시 빌드한다.

## 새 코드 흐름

| 단계 | 구현 |
|---|---|
| 브라우저 | 최초 표시·pathname 이동·숨김 탭 최초 표시 시 화면 분류 이벤트. 재렌더·prefetch·쿼리/해시만 바뀐 이동 제외 |
| 방문자 | origin별 localStorage 임의 UUID, 90일 후 교체. 차단된 저장소에서는 수집 생략 |
| API | 허용 Host·동일 Origin·JSON 1KiB·UUID·페이지 분류 검증. 사이트는 본문이 아닌 Host로 결정 |
| 제외 | 관리자 화면·인증된 관리자 방문·식별된 봇·GPC/DNT·`bp_analytics_optout=1` 환경 |
| 저장 | 전용 DB 연결 `ANALYTICS_DATABASE_URL`. 사이트+ID를 전용 키로 HMAC 처리. raw IP/실명/주문번호/URL query 저장 안 함 |
| 세션 | 마지막 수집 페이지 조회와 30분 간격. DB advisory lock으로 동일 방문자의 여러 탭 직렬화 |
| 중복·제한 | `(site,event_id)` 유일키. 동일 이벤트 재전송은 세션까지 증가시키지 않음. 방문자당 분당 60건 및 프로세스당 분당 3,000건 상한 |
| 조회 | 관리자 인증 후 접속 도메인의 기간별 distinct 방문자/세션·PV·페이지 유형·일별 집계. 오늘·최근 7일·30일 |
| 장애 | 수집 실패는 구매 흐름과 분리. 조회 실패를 0으로 표시하지 않음. 저장 오류 로그에는 고정 오류 코드만 남김 |

실제 사람 수/모든 조회를 보장하지 않는다. 식별값 초기화/기기 변경/봇 위장/수집 차단·오프라인에 따른 차이가 있다. 스크롤·화면 체류만으로 세션을 연장하지 않는다. 미등록 경로/결제 완료 화면은 수집하지 않고 전환율로 계산하지 않는다. 일반 사용자가 고객 화면을 새로고침하면 새 페이지 조회다.

## 활성화할 때 필요한 작업 (이번에는 미실행)

1. 최신 main 위에 이번 변경만 병합하고 전체 검증. 별도 외부 계정 가입은 필요 없음.
2. 통계용 PostgreSQL DB/접속 계정을 지정하고 `ops/sql/visit-analytics.sql`을 대상 DB에 실행. 주문 DB를 자동 사용하지 않음.
3. `ANALYTICS_DATABASE_URL`과 별도 무작위 `ANALYTICS_HASH_SECRET`(32자 이상) 설정. 전용 계정에는 필요한 테이블 조회/삽입/갱신 권한만 부여. TLS 연결 URL 사용.
4. 보관 정책 확인: 원시 방문 이벤트 90일 기준 정리 SQL(`ops/sql/visit-analytics-retention.sql`) 준비. 스케줄은 미가동이며 실행 주기 연결 필요. 브라우저 ID 교체 기간과 서버 보관 기간은 별개.
5. 운영 배포 후 수집 활성화 지시 범위에 맞춰 `ANALYTICS_ENABLED=true` 설정하고 앱 재시작. 설정 누락 시 API는 503, 화면은 연결 준비로 표시.
6. 두 사이트에서 수동 방문 → 수신·세션·관리자 조회 확인. 새 로그 수집 목적·기간을 운영 개인정보 안내에 맞춰 반영한 후 활성화.
7. 서버 트래픽은 별도 Nginx 로그 설정·정기 집계, 자동 점검은 cron 활성화가 필요. 자동 알림·실행 누락 감시·관리자 결과 자동 전달은 아직 미구현.

키 변경 시 이전 방문자와 새 방문자는 합쳐지지 않는다. `ANALYTICS_ENABLED=false`로 수집을 중단할 수 있으며 기존 데이터가 삭제되는 것은 아니다. 중단 상태에서는 관리자 집계도 숨긴다.
