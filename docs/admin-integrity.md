# 관리자 정합성 수정 / 2026-09-08

상품 등록·주문·매출·정산 감사의 A1~A12를 수정했다. 배포 전 검토본이며 운영 DB 수정은 수행하지 않았다.

## 계산 기준

- `order-finance.ts`: 배송 상태와 결제 상태를 분리해 실제 결제와 환불 기록으로 집계한다.
- 손익/인플루언서 수수료는 배송비를 제외한 상품 금액 기준이다. 전시/비전시 및 정산 입금 예상은 고객 결제 총액 기준이므로 배송비만큼 차이가 날 수 있다.
- 기존 환불에는 상품별 차감액이 없다. 상품 매출에서 먼저 환불액을 빼고 남는 환불은 배송비에 적용한다. 상품이 여러 개면 상품 금액 비중으로 나누되 원 단위 합계가 맞도록 배분한다. 특정 상품 환불과의 정확한 대응이 필요한 경우 항목별 환불 내역이 추가로 필요하다.
- 신규 주문은 상품/추가상품별 공급가·수수료율·과세 구분을 저장한다. 과거 수수료는 기존 주문 당시 요율을 사용한다. 현재 상품 요율이나 과세 구분으로 과거 값을 임의 보정하지 않는다.
- 원가/과세/요율/환불액이 미확인인 경우 매출을 숨기지 않고 순이익 또는 정산 확정을 보류한다. 환불만으로 공급사 매입원가가 회수됐다고 가정하지 않는다.
- 배송 시 생성한 수수료는 예상이다. 실제 PG 수수료로 확인된 데이터와 구분한다.

## 결제 복구

상품 결제 승인 전에 서버 검증, 재고 예약, `payment_attempts` 저장을 한 트랜잭션으로 처리한다. 결제 시도별 고유 키와 저장된 주문 스냅샷으로 같은 요청의 중복 주문·재고 차감을 막는다.

승인 결과가 불명확하거나 승인 후 주문 저장이 실패하면 재고를 바로 풀지 않는다. 고객의 동일 요청 재시도 또는 관리자 `/admin/payment-recovery`의 **결제사 확인·복구**로 결제사를 조회한다. 승인 완료가 확인되면 주문을 복구하고, 실패·취소가 확정되면 예약 재고를 한 번만 복원한다. 관리자 복구 버튼은 새 결제를 승인하지 않는다. PG 조회가 계속 실패하거나 결제가 아직 진행 중이면 확인 대상으로 유지한다. 무인 주기 복구 스케줄은 이번 변경에서 가동하지 않는다.

## 배포 준비

`npm run test:admin-integrity`는 운영 DB 없이 PGlite와 외부 API 모의 응답을 사용한다. 기존 배포 워크플로에도 테스트가 포함되어 실패 시 마이그레이션·빌드·재시작 전에 중단한다.

`migrate-order-site.cjs`가 `admin-integrity.sql`을 추가 실행한다. 새 앱을 실행하기 전에 마이그레이션해야 한다. 컬럼/테이블을 추가하며 상품·주문·지급 이력을 삭제하지 않는다. 상품 삭제는 보관 처리로 전환한다.

결제 승인 멱등키와 상태 조회 동작은 [토스 공식 인증·헤더 문서](https://docs.tosspayments.com/reference/using-api/authorization) 및 [코어 API](https://docs.tosspayments.com/reference)를 기준으로 구현했다. 실제 PG 테스트 키를 이용한 통합 결제는 별도 검증 대상이다.
