# 상품 노출과 배송 예외 자동화

## 적용 범위
- 산지픽: 판매 중·재고 있는 상품만 배너/추천. 등록 상품이 없으면 준비 안내, 조회 실패면 재시도. 공개 demo 상세는 404.
- 정가 대비 할인만 표시하고 후기 없는 별점을 제거. 블랜드픽 예시 AI 트렌드 숨김(네이버 연동 보류 유지).
- 송장 엑셀 import 트랜잭션에 발송 대기를 함께 저장. 기존 주문을 소급 발송하지 않는다.
- 한 주문에 한 발송 안내. 앞자리 0을 포함한 송장 문자열을 보존한다.
- 발송업체의 명시적인 속도 제한(429)은 재시도. 최대 5회, 15/30/60/120분 간격으로 다음 대상 시각 설정. 30분 주기 작업에서 실행되므로 실제 실행은 늦어질 수 있다.
- 네트워크 단절·알 수 없는 응답·전송 도중 프로세스 종료는 `review`. 발송업체에서 접수 이력을 확인하기 전에는 자동 재발송하지 않는다.
- `sent`는 발송 접수 성공이며 최종 수신 여부를 의미하지 않는다. 관리자 ‘접수 확인 완료’도 공급자 이력을 대조한 후에만 사용한다.
- 다른 사이트 주문·취소 주문·변경된 송장의 이전 안내는 발송하지 않는다. 처리 완료 시 메시지 본문을 비운다.
- 수동 배송 조회/정기 조회 모두 결과를 기록. 정기 작업은 동일 송장 조회 후 12시간 대기, 기존 1일 2회 일정과 건수 제한 유지. 수동 조회는 배송관리에서 실행 가능.
- 오늘 처리할 일 및 배송관리에서 실패 수·마지막 조회·다음 자동 처리 대상 시각 확인. 개인정보 포함 공급자 오류 전문은 저장하지 않는다.
- 사이트 점검: 기존 HTTP/인증/상품 표본 + 공개 일반 링크 최대 8개, 같은 도메인 이미지 최대 6개, 배너의 지정 상품/링크 일치 확인. 전체 링크 크롤링 또는 브라우저 레이아웃 검증은 아니다.

## 배포와 가동
1. 기존 배포 절차에서 `node scripts/prepare-commerce-automation.cjs`가 새 테이블을 준비한다. 기존 주문/정산 금액을 변경하지 않는 반복 실행 가능한 마이그레이션이다.
2. 앱 빌드/재시작 후 새 송장 import부터 큐에 쌓인다. SOLAPI 설정이 없으면 발송하지 않고 대기로 남는다.
3. `Retry Shipment Notifications`는 main에 반영 후 매시 7분/37분 서버 작업을 실행한다. 실제 고객 발송이 발생하므로 배포 전 테스트 주문과 설정을 확인한다.
4. `/admin/shipment-notifications`에서 결과 불명확 건의 공급자 접수 이력을 대조한다. 미접수가 확인된 경우에만 재시도 예약한다.
5. 되돌릴 때는 알림 워크플로를 먼저 비활성화하고 이전 앱을 복원한다. 새 테이블은 남겨 이력을 보존한다. 큐 삭제나 주문 역변경은 하지 않는다.

## 검증
`npm run test:commerce-automation`
`node --test --test-concurrency=1 tests/full-process-edges.cjs tests/shipping-simulation.cjs tests/admin-final-process.cjs`
`npm run build -- --webpack`
테스트는 PGlite 격리 DB/가짜 발송 함수를 사용한다. 실제 발송·PG 결제·운영 DB 테스트가 아니다.

## 별도 인프라 확인 항목
DB/업로드 파일의 AWS 백업 설정은 이 저장소만으로 확인할 수 없다. 정기 백업의 최근 성공 시각, 보관 주기, 별도 환경 복원 시험을 확인해야 한다. 현재는 백업을 구축했다고 표시하지 않는다. 카카오 발송업체·승인 템플릿과 네이버 연동도 이번에 활성화하지 않는다.
