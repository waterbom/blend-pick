# 단궁 예약 운영 및 학습 로드맵

## 판매 전 입력할 값

관리자 → 공구 운영 → 단궁 예약·요금에서 설정합니다.

- 확정 숙박료와 날짜: 시작일 포함, 종료일 제외. 금·토 요금 분리. 공휴일 전일 등은 날짜 하나를 별도로 덮어씁니다.
- 6인 초과 요금의 적용 단위(1박당/예약당), 바비큐 세팅 예약당 요금
- 보증금 금액, 납부·반환 조건, 기타 현장 추가 비용
- 고객에게 제공할 확정 취소·환불 규정
- 최소 준비일 및 최대 숙박일

초기 스키마는 판매 중지 및 날짜별 요금 없음으로 생성합니다. PDF의 제시가나 소비자분쟁해결 참고 기간을 확정 판매가·시즌 날짜로 자동 적용하지 않습니다. 기존 설정은 재배포로 초기화하지 않습니다. 실결제 키가 없거나 필수 운영 조건이 미정이면 판매를 켤 수 없습니다.

## 실무 흐름과 코드

| 단계 | 기술·코드 | 실무에서 하는 일 |
|---|---|---|
| 상품 소개 | Next.js 서버 컴포넌트, `app/hotel/dangung/page.tsx` | 검색 가능한 소개 문구와 원본 사진 22장 제공 |
| 사계·객실 | React `Interactions.tsx`, scoped CSS | 사계 4초 반복, 일시정지, 모션 감소 설정 존중, 원본 비율 사진 확대 |
| 날짜 선택 | React `Booking.tsx`, GET `/api/dangung` | 판매일·가격·예약된 날짜 조회, 모바일 달력에서 입실·퇴실 선택 |
| 금액 계산 | `dangung-core.cjs`의 `quote()` | 퇴실일 제외한 1박 요금 합산, 인원·바비큐 비용 추가, 보증금 별도 안내 |
| 날짜 확보 | `reserve()`, PostgreSQL transaction/row lock | 설정 행 잠금, 중복 요청 ID 검증, 날짜별 유일 제약으로 이중 예약 방지 |
| 결제창 | Toss Payments SDK `requestPayment()` | 서버가 발급한 예약 ID와 금액으로 카드 결제창 호출 |
| 승인 | `confirm()`, 토스 서버 승인 API | 소유권·금액 검증 후 승인. 안정적인 Idempotency-Key로 재시도 중복 승인 방지 |
| 예약 확정 | `finish()` | 승인 결과의 주문·금액·통화 검증, 결제 상태와 영수증 저장 |
| 장애 복구 | `reconcile()` | 토스 주문 조회로 승인/환불 결과를 재확인. 확인 중인 날짜는 자동 해제하지 않음 |
| 취소·환불 | 고객 취소 요청 → 관리자 `cancel()` | 예약 시 동의한 규정과 금액 확인, 전액/부분/0원 환불 처리 및 날짜 반환 |
| 검증 | Node test runner + PGlite + Next build + 운영 확인 | 계산/인증 → 격리 DB·결제 장애 → 배포 후 실제 페이지 확인 |

## 데이터와 상태

- `dangung_settings`: 판매 조건 및 규정 버전
- `dangung_dates`: 날짜별 확정 숙박료와 판매 여부
- `dangung_reservations`: 예약자, 가격·규정 스냅샷, 결제 상태
- `dangung_occupancy`: 1개 독채의 날짜별 예약 점유. `day` 기본키로 이중 점유 차단
- `dangung_audit`: 요금 변경, 예약, 결제·취소 처리 이력

`pending`은 15분 후 만료되어 날짜가 다시 판매됩니다. `confirming`은 결제 승인 요청이 시작된 상태이며, 응답이 유실돼도 실제 결제가 되었을 가능성이 있어 자동 만료시키지 않습니다. 고객의 다시 확인 또는 관리자 결제 상태 복구로 토스에 조회합니다. `paid`는 확정, `cancelling`은 환불 확인 중, `cancelled`는 예약 취소 완료입니다.

단궁은 유탑 재고/취소 규정과 분리한 예약 원장을 사용합니다. 단궁 매출·예약 현황은 전용 관리자 화면에서 집계하며 일반 상품 배송·유탑 정산 원장에 혼합하지 않습니다. 관리자 취소 시 일부 금액만 환불해도 해당 숙박 예약 전체는 취소되고, 차액은 취소 수수료 수입으로 남습니다.

## 운영 확인

1. 운영 조건과 날짜별 요금을 입력하고 달력의 판매 금액을 확인합니다.
2. 토스 실결제 설정 확인 후 판매를 켭니다.
3. 실제 카드 승인은 운영자가 본인 카드로 최종 확인합니다. 개발 테스트는 가상 결제 응답과 격리 DB를 사용하며 실카드를 청구하지 않습니다.
4. 예약한 브라우저에서 예약번호로 결과 조회가 가능합니다. 다른 기기·쿠키 삭제 시 고객센터에서 예약번호와 연락처로 확인합니다.
5. 승인/환불 확인 필요 상태는 관리자에서 복구합니다. 토스 조회도 실패하면 날짜 점유를 임의 삭제하지 않고 결제 내역을 확인합니다.

## 검증 범위

`npm run test:dangung`은 날짜 경계, 확정 요금, 인원·옵션, 마감일, 쿠키 소유권, 관리자·사이트 분리, 중복 예약·콜백, 만료, 승인 후 응답 유실/DB 실패, 전액·부분·0원 환불을 검사합니다.

PGlite는 격리된 PostgreSQL 엔진입니다. 트랜잭션 연결 어댑터는 단일 DB 연결을 직렬화하며, 운영 PostgreSQL 다중 연결 부하 시험이나 토스 실카드 승인을 대체하지 않습니다. 운영 확인은 공개 페이지·정적 파일·접근 제어·판매 준비 상태를 조회하며 고객 주문이나 문자를 만들지 않습니다.

## 2026-09-15 판매 조건 반영

- 기준 6인·최대 16인. 36개월 미만 유아는 무료이며 기준·최대 인원에서 제외하고, 예약 내역에 인원수를 별도 기록합니다.
- 6인 초과 1인 20,000원(침구 포함)은 예약당 한 번만 계산합니다.
- 추가 옵션: 바비큐 세팅 50,000원, 64인치 모니터 50,000원. 각각 예약당 한 번 합산하며 예약 확인·결과·관리자 내역에 남깁니다.
- 시설 보증금 100,000원은 카드 결제에 합산하지 않고 계좌이체로 별도 납부합니다. 실제 계좌는 운영자가 추후 제공할 예정입니다.
- 운영자가 제공한 취소·환불 및 시설 보증금 문구는 공개 페이지와 예약 동의 화면에 표시하고 예약 당시 내용으로 보관합니다. 취소·환불 금액은 기존처럼 관리자가 확인 후 처리하며 자동 환불 규정 해석은 추가하지 않았습니다.
- `lib/dangung-policy.cjs`의 확정 조건은 배포 준비 과정에서 한 번 적용합니다. 이후 재배포는 관리자 변경값과 기존 예약 규정 스냅샷을 덮어쓰지 않습니다.
- 주말 추가금 100,000원 / 준성수기 100,000원 / 극성수기 150,000원은 저장합니다. 기본 1박 요금, 시즌 날짜 및 주말·시즌 중복 가산 여부는 미확정이므로 날짜별 판매가를 임의 생성하지 않습니다.
- 상시·블랜드픽 단독 판매 방침. 날짜별 판매 시작 전 기본 요금과 시즌 규칙을 확정해야 합니다. 이 변경은 판매 스위치를 켜지 않습니다.
